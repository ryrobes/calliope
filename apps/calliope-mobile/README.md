# Calliope Mobile experiment

A real Android/GPUI client, with an iOS Simulator host, for **Callie conversations and published company apps**. This is
a feasibility probe, not the complete desktop canvas client. It reads the
same A2UI catalog and renderer source, PublishedApps runtime, filter logic, and
theme loader as `../calliope-canvas`. SQL, decisions, app definitions, versions,
and writes stay on the Calliope server. No local demo server or SQLite database.

The working desktop build retains GPUI 0.2.2 / gpui-component 0.5.1. This separate
workspace pins a mutually compatible GPUI 0.3.8 / GPUI Kit 0.7.1 mobile stack,
including community touch/lifecycle fixes. `renderer/Cargo.toml` compiles the
existing renderer files with a small `gpui-next` compatibility feature. It does
not fork the catalog or maintain a second renderer implementation.

The [iOS build and inspection guide](ios/README.md) uses the same app runtime
inside UIKit with Metal rendering, Keychain storage and direct HTTPS access.
That Simulator host is a feasibility check with remaining iOS gaps; it is not a
claim of Android feature parity or App Store readiness.

## Ask Callie and conversations

The bottom navigation has **Ask Callie**, **Apps**, and **Account**. Ask Callie
lists the signed-in user's owned, non-archived server threads, searchable by title
and synopsis. Open a thread to read its history or continue it, or choose **New
chat**. A new server conversation is created only when the first message is sent;
its title is generated by the existing server mechanism. Streams, stop and
reattachment use the same turn endpoints as the contextual app assistant.
Mirrored messaging-channel threads remain view only.

**Stage** lists current visible work objects, folding superseded versions within
the same lineage. Category filters and expandable previews show saved query rows,
images and text/JSON files directly; native app items can open under Apps. Full
interactive dashboards retain their exact thread/surface links in the OS browser. The
browser uses its own login. Contextual Ask Callie inside a company app remains
available separately with its record context and reviewable field suggestions.

Sent history stays on the server and is available across clients. Unsent chat
text survives tab/thread changes while the process is running; it is not yet a
persistent offline chat outbox. This differs from the durable company-app record
drafts. General chat now shares dictation and read-aloud with contextual chat,
adds Copy reply, and initially renders the most recent 20 exchanges with an
explicit control for older history.

Run the structural smoke test using the existing account and thread APIs:

```sh
python3 check_conversations.py --serial DEVICE_SERIAL --adb /path/to/adb
# On the Mac:
python3 check_conversations.py --device SIMULATOR_UUID
```

`--session` selects an owned thread to inspect. `--send` explicitly creates a
new conversation and sends one harmless test question; without it, the check
makes no conversation/business writes. Real IME, rotation, browser handoff and
screenshots complement this test.

## Run on the connected phone

The installed launcher entry is **Calliope Mobile**, package
`ai.rvbbit.calliope.mobile`. A LAN instance can use a direct HTTPS origin, for
example `https://calliope.local`. Install that instance's internal CA on Android
(see [behind your own HTTPS proxy](../../deploy/README.md#behind-your-own-https-proxy))
and sign in through **Account**. Publicly trusted HTTPS instances need no
internal CA installation. USB is for builds and inspection, not a
requirement for using the app.

For optional development through a desktop SSH tunnel, use
`adb -s SERIAL reverse tcp:18080 tcp:18080`. That loopback URL is a provisioned
test address, not the client's default or a local application server. Its route
is phone `127.0.0.1:18080`
→ ADB over USB → desktop `127.0.0.1:18080` → SSH to the server host's port 8080
→ its normal origin gateway → Calliope. The client sends the existing Calliope
API requests through those transport forwards; no companion API is involved.
Normal LAN use goes straight to the server host's HTTPS ingress and bypasses
both ADB and the desktop tunnel. The server must include the native chart
endpoint described below.

```sh
cd apps/calliope-mobile
./build.sh
# Choose the authorized phone explicitly from `adb devices -l`.
python provision.py --serial DEVICE_SERIAL
```

`dist/calliope-mobile.apk` is an optimized ARM64 APK, **debug-signed and
debuggable for sideload testing**. It is not a store release. Provisioning reads
the existing desktop connection by default, verifies its app endpoint, and puts
the session into Android's private app directory using `run-as`. No credentials
are compiled into the APK or written to shared phone storage. On first launch,
the provisioned session is encrypted with an Android Keystore AES-GCM key and
the temporary plaintext connection file is removed. Uninstalling the
app removes its private files. Backups are disabled.

Build prerequisites: Rust 1.98.0 with `aarch64-linux-android`, cargo-ndk, JDK 17,
Android platform 35, build tools 36.0.0 (AGP downloads them), and NDK
27.2.12479018. Gradle 9.4.1 is supplied by the wrapper. The local experiment's
toolchain lives under `~/.local/share/calliope-mobile`; `build.sh` recognizes it
without changing the system Rust/Java installation. Override `ANDROID_HOME`,
`ANDROID_NDK_HOME`, and `CALLIOPE_ANDROID_JAVA_HOME` for another setup.

## Device evidence

Tested on a Samsung Galaxy S-series phone, Android 16/API 36, ARM64. GPUI's own
renderer log selected **Adreno 740 (Vulkan)**. This is hardware rendering, not an
emulator or a webview.

| Check | Result |
| --- | --- |
| Company-app tiles | 13 published entries; two columns on this phone, responsive columns on desktop |
| Eleven demo surfaces | Loaded through the same server contract; no SQL/runtime failures |
| SQL filter on change | 30 visits → 7 for Cedar, without Apply |
| Keyboard / composition | SwiftKey opens; viewport shrinks and reveals the focused input; composing text stays visible; committed text updates SQL |
| Record selection | Exactly one selected visit after changing records |
| Decision region | Parts → comeback; unsaved notes retained |
| Home and resume | GPU surface reattached; same process and unsaved draft retained |
| Theme | Server palette and custom fonts loaded; GPUI Kit's new paint-token projection synchronized |
| Charts | All 21 gallery families rendered on the phone; physical tap tooltip and SQL filter on change verified |
| Android navigation | Back returns to tiles, then backgrounds the app; Web opens the OS browser |
| Linux regression | 53 tests passed, one existing ignored; desktop dependencies unchanged |

Evidence from each device run goes to ignored `dist/evidence/`: screenshots,
`verification.json`, and the separately observed `ime-verification.json`.
The semantic test never presses business Save/Submit actions. Loading a page
does not imply every control on it has been exercised or looks good at phone
width. No sustained frame-time, battery, or thermal benchmark has been run.

## Gaps exposed by the experiment

- **Phone layout:** desktop navigation, page introductions, and filter stacks
  consume too much height. Dense grids, independent scroll regions, record
  inspectors, and touch targets need a deliberate compact presentation. The
  renderer can stack containers; that alone is not a good phone workflow.
- **Chart interactions:** rectangle and circle/square marks support picking and
  tooltips. Lines, arcs, geoshapes and other marks render, but do not all have
  picking geometry. Vega brush/selection widgets remain web interactions.
- **OS integration:** browser Intent handoff is connected. The browser keeps its
  own login session and certificate trust; app cookies are never transferred.
  The Android document picker and authenticated attachment downloads now work.
  Direct camera capture now uses the system camera; authenticated app-link return flows remain to be added.
- **Input:** the Kit splits Input and Textarea state. Field kinds now choose the
  Android keyboard (number/decimal, date/time, email/URL/password, or multiline).
  Shared date/time pickers retain the ordinary model bindings. Other IMEs,
  accessibility and multitouch still need broader checks.
- **Lifecycle:** per-record drafts, navigation history and pending submissions
  survive process death. SQL polling pauses in the background and reads refresh
  on resume. Long suspend/resume cycles and background power use still need broader testing.
- **Product shell:** contextual Callie chat, TTS/STT, and Android microphone
  permission handling are implemented. Voice works on a physical Android phone;
  interruptions, audio routing and long sessions still need broader
  device checks. The desktop's full personal canvas and notifications remain
  outside this phone shell. Offline support is scoped to
  previously opened app workspaces; see [native drafts](../calliope-canvas/OFFLINE.md).
- **Release readiness:** community forks are pinned for compatibility. Target
  SDK 34 avoids forced edge-to-edge for this initial probe; current SDK insets,
  TalkBack, accessibility semantics, store packaging/signing and 16 KB device
  execution remain unvalidated. The native library has 16 KB ELF segment
  alignment, but the test phone uses 4 KB pages. iOS has been exercised only in
  the Simulator; physical-device limits remain open.

The useful next slice is a phone-oriented field visit: visit list → work area →
notes/photos/Callie, retaining the same SQL and action contracts. Prove that
complete flow before porting every desktop surface.

The current delivery checks exercise that flow.
`check_voice.py --serial SERIAL --slug APP --live-voice --output DIR`
tests actual Android recording/playback cancellation, backgrounding and denied/
re-enabled microphone permission using a completed contextual reply. It restores
permission after the test, records host audio state, and submits no business data.
It does not replace a human check of dictation accuracy or speaker audibility.

## Chart rendering contract

Published apps on **both desktop and Android** send resolved inline Vega-Lite to
`POST /api/calliope/ui-charts/render`. Calliope returns a 2× PNG and mark geometry
from the pinned `vl-convert-python==1.9.0` engine (Vega-Lite 6.1). GPUI composites
the image and handles tooltips/taps locally. Resize and data changes request a
fresh image asynchronously; a generation check discards outdated responses.
This is native display and input with server-side rasterization, not a WebView.

The server checks mapped sessions and request origins, rejects external chart
URLs/image marks, bounds input and output, and limits conversion to two child
processes with time/CPU/file/RSS budgets. Results have a short actor-scoped memory
cache and `Cache-Control: no-store`. Temporary conversion files are removed.
Server typography comes from its existing `theme/fonts` directory. The historical
fixture host still uses the same worker locally; published apps need no Python
installation on the client. Failed charts offer tap-to-retry or the shell's
Refresh action; opening an app starts with fresh chart entities.

## USB testing without controlling the Linux desktop

The app exposes the existing structural driver through a Unix socket in its
private sandbox. A tiny ARM64 client connects via `adb shell -T run-as`; there
is no TCP test service or exported Android component. This is intentionally a
test-build facility. The request semantics match the desktop probe. The shared shell also accepts
`home` and `open_app` (with a published `slug`) for deterministic navigation;
`inspect` reports app metadata and the measured tile-column count.

```sh
printf '%s\n' '{"op":"inspect"}' | python probe.py --serial DEVICE_SERIAL
# Open one of the Demo apps on the phone first.
python smoke.py --serial DEVICE_SERIAL
# From tiles: all SQL chart families, filter changes and a physical tap.
python check_charts.py --serial DEVICE_SERIAL
```

`smoke.py` tests binding/selection/decision/state continuity and navigates eleven
demo pages. It captures real phone screenshots but uses semantic fills for
its data assertions; these do not replace touch, IME, or accessibility tests.
Use ADB screenshots and input for those. `exec-out` is suitable for screenshots;
the structural client requires `shell -T` so request stdin reaches the process.

See [THIRD_PARTY.md](THIRD_PARTY.md) for dependency provenance and licenses.

## Native connection and field evidence

Tap **Account** to sign in with the existing Calliope server/email/password flow.
A blank install opens this screen directly. HTTPS is required except for the
local ADB tunnel. Passwords are cleared after submission and never persisted;
the session is saved in `connection.enc`, encrypted by an Android Keystore key.
This supports the existing password login; OAuth callback handling is still a
separate mobile integration. The native HTTP client uses Android's configured
system and user CA roots, with normal chain, expiry and hostname validation.
An instance's internal CA is installed in Android Settings, never baked into
the APK. Restart the app after a certificate-store change. Connection errors
include their underlying DNS/TLS/network cause to make setup failures diagnosable.
Saved reports remain on Calliope; unsent drafts survive restarts on the device.

The Field notebook demonstrates the shared `CAttachments` component. Choose a
PNG/JPEG photo, PDF, or UTF-8 text file (5 MB each, five per component), then
**Submit report**. Android uses `ACTION_OPEN_DOCUMENT`, without broad storage
permissions. Cancel preserves the draft. A submitted report shows read-only
attachment links; opening one downloads it using the app session and hands a
read-only FileProvider URI to a device viewer. The viewer receives no cookie.
Use **Take photo** for the system camera. Confirmed photos are rotated upright,
resized to at most 2048 pixels on the longest edge, and encoded as JPEG without
camera metadata. They stay in the private draft store until an explicit action
needs to send them. See [native drafts](../calliope-canvas/OFFLINE.md) for recovery,
submission semantics, and current limits.

Files and metadata live in Calliope's Postgres under the owning app's access
rules. A file uploaded through one app is accessible from another surface only
if the viewer can still access the owning app. Uploading does not submit a
report; the explicit versioned SQL action stores its file IDs. Draft removal
only removes a reference, preserving evidence used by existing receipts.

Verified on a physical Android phone: wrong-password rejection, native sign-in,
encrypted session migration, process restart and APK update, document picker
selection/cancel, photo upload, report submission/reset, and reopening evidence.
The phone's saved report also renders in web and Linux GPUI. Generated fixtures
contain no customer data. Regression evidence is written under `dist/evidence`
or the task's temporary test directory and is not committed.

The private driver accepts `account`, then `fill` with `id` `server`, `email`, or
`password`, and `press` with `id` `connect` or `cancel`. Connection inspection
reports only whether a password exists, never its value or the session cookie.
`press` on a `CAttachments` component opens the system picker; include `file` with
one of that component's IDs to open existing evidence. These use real host
handlers, not simulated uploads.

Camera capture follows Android's [camera intent](https://developer.android.com/media/camera/camera-intents)
flow with a scoped FileProvider output URI. There is no embedded camera view,
Camera permission, broad storage permission, or automatic gallery publication.
The private driver can use `{"op":"press","id":"page.evidence","camera":true}`
to open the real camera. The user still confirms the shot in the camera app.
The shell accepts `refresh` and `send_pending`; `inspect` reports `offline`,
`pending`, `draft_saved`, and `draft_error` for deterministic recovery checks.

### Camera and offline verification

On a physical Android phone, verified camera cancel, confirmed capture, and
recovery after killing Calliope while the camera confirmation screen was open. A
covered-lens test JPEG, notes and readings survived offline restarts. A pending
submission survived a second restart, retained its UUID, and committed only
after explicit Send pending. Postgres contained exactly one report; its photo
hash matched the local capture. Replaying the committed request returned its
receipt without adding a report. A server-rejected empty report left the draft
editable. Page changes and live refresh retained staged evidence for the same
selected record.

A repeatable test deliberately creates **one labeled demo report**:

```sh
# Open Demo Field Notebook with a blank report and a confirmed test photo.
python check_offline.py --serial DEVICE_SERIAL --submit-demo-report --require-evidence
```

The test restores the ADB reverse mapping in `finally`, checks durable notes and
readings, restarts before and after offline Submit, verifies the pending editor
is frozen, and explicitly resends. It never changes global device networking.

### Record workspaces and recovery

The shared desktop/Android shell now provides **Back**, **Drafts**, per-record
Discard, cached navigation, and automatic read reconnection with bounded backoff.
Android Back walks app history before returning to the tiles. Unsent work remains
local until explicit Submit/Send pending. See [native drafts](../calliope-canvas/OFFLINE.md)
for the cache, version and pending-command limits.

The private driver also accepts `back`, `resume_draft` and `discard_draft` (the
last two with a `key` returned by inspection). `discard_draft` opens confirmation;
`confirm_discard` commits it and `back` cancels it. Inspection exposes `drafts`,
`history_depth`, `foreground`, `read_requests`, `retry_attempts`, and `fetched_at`.
These exercise the same handlers as the toolbar and Android navigation.

Repeat the native recovery check with the phone unlocked and a blank Field
notebook report open (the default test makes no business submission):

```sh
python check_workspaces.py --serial DEVICE_SERIAL --output dist/workspaces
# To additionally submit one labeled fictional report:
python check_workspaces.py --serial DEVICE_SERIAL --output dist/workspaces-submit --submit-demo-report
```

The desktop equivalent uses a disposable profile and private Xvfb display:
`python ../calliope-canvas/business/check_workspaces.py --output /tmp/workspace-check`.

Verified on a physical Android phone: A → B → physical Back to A, cached record
selection and Back offline, process-death recovery, automatic read reconnect, 35
seconds backgrounded with exactly one refresh on resume, a photo attached
offline through the system picker surviving restart, and explicit submission of
one report while another record's draft remained intact. The pending request key
survived restart; reconnecting did not submit it. Back also restored the filter,
page offset and independent job-list offset after changing records. These are
foreground recovery checks, not a battery or long-duration background-execution
benchmark.

### App shell and input checks

App tiles have local name/description search, content-driven height and separate
empty/loading/no-match states. The compact header keeps secondary actions in
**More**. Status details expand on demand; failures, unsaved-on-disk errors and
pending submissions stay visible. **Account** shows the current identity and
server; **Change connection** explicitly opens the sign-in form. A loopback
connection is labeled as USB testing.

Typed fields share date/time pickers, validation and first-invalid-field focus.
Tab/Shift-Tab move among editable text fields. This does not establish complete
keyboard or screen-reader accessibility for the entire component catalog.
The private renderer probe exposes `inputs` bounds, `focused_input`, `input_kind`,
`field_errors` and `picker` in `render`; `focus` and `picker` take a component `id`.
The app shell accepts `search` with a `value`. These use normal input state and
picker handlers rather than replacing model bindings.

The desktop input check uses physical key events on a private Xvfb display:

```sh
python ../calliope-canvas/business/check_inputs.py --output /tmp/calliope-inputs
python check_inputs.py --serial DEVICE_SERIAL --output dist/inputs
```

It checks pre-submit validation without sending a command, multiline entry,
select/copy/paste, Tab/Shift-Tab, search and picker dismissal. The disposable
profile keeps its local edits separate from the user's desktop work.
The Android check requires no existing Field notebook drafts and restores its
test edits. It verifies exact rapid text entry, multiline Return, select/copy/paste,
Tab/Shift-Tab, decimal entry and Android's reported numeric keyboard type.
Physical keys bypass predictive IMEs' transient composition buffers; software
keyboard composition still uses the InputConnection bridge.

Verified on Linux in private Xvfb and on a physical Android phone: the input and
record-recovery checks, Account cancellation, app search and picker dismissal.
Actual picker clicks updated date/time bindings on desktop. SwiftKey touch
entry also passed decimal and multiline composition checks. This is a focused
smoke test, not coverage of every IME, input language or accessibility service.
